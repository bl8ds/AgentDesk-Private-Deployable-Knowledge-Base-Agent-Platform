# 非 Go 技术栈：可快速交付的企业级落地方案

| 项 | 内容 |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-07-16 |
| 前提 | **允许非 Go**；仍要求私有化、可商用协议、半个月量级出 Phase 1、**对外可卖自研感** |
| 关联 | [01-技术方案定稿](./01-企业级Agent技术方案定稿.md)（Go 优先主路径）· [02-对接边界](./02-使用方对接与交付边界.md) |

本文回答：若团队不必死磕 Go，有哪些**更成熟、更快**的企业落地组合？如何避免「装个开源平台交差 → 谈不拢价钱」？

---

## 1. 先定交付原则（与栈无关）

无论选哪条非 Go 路线，商业上仍建议：

| 原则 | 说明 |
|------|------|
| **可见面自研** | 使用方看到的是你们的 H5 + 运营后台（或深度白标），不是开源默认控制台 |
| **引擎可开源** | 底层用成熟引擎/框架合法，合同写「定制系统 + 集成部署」 |
| **协议先审** | 尤其 Dify 等「Apache + 附加条款」；对外多租户转售可能受限 |
| **Phase 1 只做问答** | 生图/视频/复杂导购仍 Phase 2 |

## 2. 方案总览（按「交付速度 × 自研可报价性」）

| 方案 | 技术栈 | 约成熟度 | 半个月可行性 | 自研可报价性 | 一句话 |
|------|--------|----------|--------------|--------------|--------|
| **N1 推荐** | RAGFlow（黑盒）+ **Node/TS BFF** + assistant-ui | 极高（引擎） | 高 | 高 | 与定稿 A 相同，只是 BFF 改 TS，联调更快 |
| **N2 推荐（全自研感）** | **Mastra** + Next/React + assistant-ui | 高（Agent） | 高 | **很高** | 纯代码产品，几乎无「开源平台感」 |
| **N3 稳妥企业** | **LangGraph/LangChain**（Python）+ FastAPI + assistant-ui +（可选）RAGFlow 只做解析检索 | 极高（编排） | 中高 | 高 | 复杂 Agent/合规流程最强；人效略慢于 N2 |
| **N4 慎用** | **Dify 私有化** + 外挂自研 H5（只调 API） | 极高（平台） | **最高** | 中（需严格藏 UI） | 最快出活；商务与 License 要设计好 |
| **N5 不推荐作交付** | 直接把 Dify/FastGPT 控制台交给使用方 | — | 最快 | **低** | 难谈价钱，本文否决 |
| **N6 文档极强** | RAGFlow 全能力 + 自研壳（任意语言 BFF） | 极高（文档） | 高 | 高 | 复杂 PDF/表格场景首选引擎 |

与 [01 定稿](./01-企业级Agent技术方案定稿.md) 关系：  
- Go 团队默认仍用 **01 的路线 A（RAGFlow + Go BFF）**。  
- 允许非 Go 时，**同等架构的 N1** 往往更快；要「看起来全是我们写的」选 **N2**；文档极难选 **N6/N1**；平台派想极限加速且能接受 License/商务约束再评 **N4**。

## 3. 方案详解

### N1 — RAGFlow 黑盒 + TypeScript BFF + assistant-ui

**是什么**  
与主定稿同一架构，BFF 从 Go 换成 **Node/Nest 或 Hono/Fastify**。

**为何快**  
- 知识库难活仍由 RAGFlow 承担  
- TS 与 assistant-ui、SSE、前端联调同语言，半个月里前后端撕扯更少  

**交付物**  
自研 H5、自研运营后台、TS BFF、内网 RAGFlow（不对业务用户开放控制台）。

**适合**  
允许非 Go，且 Phase 1 核心是**知识库问答**、文档质量要求高。

**注意**  
运维多一个 Python/RAGFlow 组件栈；合同仍按「定制产品」表述。

---

### N2 — Mastra + React/Next + assistant-ui（全栈 TS）

**是什么**  
[Mastra](https://github.com/mastra-ai/mastra)：TypeScript Agent 框架（Agent / Workflow / Memory / RAG / 可观测），核心 **Apache-2.0**；`ee/` 企业 SSO/RBAC **不要用**（生产需商业许可），登录与权限自研。

**为何算「企业级快速交付」**  
- 开箱 Agent + RAG + 工具调用，少拼底层  
- 与 React/assistant-ui 同生态，C 端产品成型快  
- **没有**「给你一个开源运营平台」的观感，报价叙事是「我们用框架自研的应用」——**谈价钱通常优于交 Dify 控制台**

**弱点**  
- 复杂扫描件/表格解析一般弱于 RAGFlow  
- 缓解：难文档旁路 **RAGFlow 只做 ingestion/retrieval API**，Mastra 做对话与工具（混合）

**适合**  
产品形态偏 C 端助手、后续要海报/视频等 **Tool Agent**；团队能接受 TS 为主。

**Phase 1 建议范围**  
文档问答 + 引用 + 额度 + App 嵌入；工具链只留扩展点。

---

### N3 — LangGraph / LangChain（Python）+ FastAPI + assistant-ui

**是什么**  
Python 生态事实标准：LangChain 积木 + **LangGraph** 状态机 Agent（MIT，生产案例多）。对外仍用自研 H5；API 用 FastAPI。

**为何成熟**  
- 检索、评测、护栏、可观测（LangSmith 等）资料与案例最多  
- 适合后续「多步审批、人机协同、复杂工作流」  

**速度**  
比 N2/N4 略慢（要自己拼服务与前端），但比纯 Go 自建 RAG **更快达到可靠**。

**增强**  
文档难 → 检索层接 RAGFlow 或专用解析，Graph 只编排。

**适合**  
中长期要强 Agent/合规编排；团队有 Python。

---

### N4 — Dify 作引擎（API only）+ 自研壳

**是什么**  
Dify：可视化 LLM 应用平台（工作流、知识库、模型管理、API）。社区极大，私有化 Compose 成熟。

**为何「快」**  
知识库 + 对话应用配置化，**出可问 Demo 往往最快**。

**商务与 License 风险（必读）**  
- 协议多为 **Apache + 附加条款**（常见限制：不得直接做成多租户对外 SaaS 转售；控制台品牌标识等——**以当时官方 LICENSE 为准**）  
- **把 Dify 控制台当交付后台 → 难谈自研价钱**（见 N5）  
- 正确用法：Dify **仅内网**；业务用户与使用方运营只进**你们的后台/H5**；你们调 Dify API  

**适合**  
内部要极限赶工，且法务确认 License 与「非转售 SaaS」模式匹配；仍坚持自研可见面。

**不适合**  
希望对外宣传「100% 自研平台」、或商业模式接近「转售 AI 平台」。

---

### N5 — 直接交付开源平台控制台（否决）

部署 Dify / FastGPT / RAGFlow 官方 UI 给使用方当产品。

- 工期最短，但 **集成商叙事**，人天与产品溢价都难谈  
- 与「平台方自研交付」定位冲突  
- **本文明确不推荐**

---

### N6 — 文档场景拉满：RAGFlow 为核 + 任意自研壳

当使用方语料以 **复杂 PDF、表格、版式混乱** 为主时：  
无论 BFF 是 Go / TS / Python，**检索与解析优先 RAGFlow**，前端仍 assistant-ui。  
这是「允许非 Go」时与主定稿差异最小、文档质量上限最高的路径。

## 4. 前端与集成（各方案共用）

| 层 | 建议 |
|----|------|
| C 端 UI | **assistant-ui**（生产对话）；不要用 Vercel AI SDK 模板当成品 |

## 5. 怎么选（决策树）

```
要半个月稳上知识库问答？
 ├─ 文档很复杂（PDF/表） → N1 或 N6（RAGFlow 黑盒 + 自研壳）
 ├─ 更看重「纯自研产品感」+ 后续 Agent 工具 → N2（Mastra）
 ├─ 后续强工作流/合规多步 → N3（LangGraph）
 ├─ 只要最快配置出活，且能接受 License/藏 UI → N4（Dify API）
 └─ 想直接交开源后台 → 停，选 N5 以外的路
```

**与 Go 主路径对照**  
| 诉求 | 选 |
|------|-----|
| 团队死磕 Go | [01 定稿路线 A](./01-企业级Agent技术方案定稿.md) |
| 允许非 Go，同样架构更快联调 | **N1** |
| 允许非 Go，最大化自研叙事与 Agent 扩展 | **N2** |
| 文档地狱 | **N6 / N1** |

## 7. 报价与话术（非 Go 场景）

| 做法 | 使用方感知 | 报价空间 |
|------|----------|----------|
| 交 Dify/FastGPT 控制台 | 「买了个开源」 | 窄 |

## 9. 专题：Mastra 是什么 + 与自有 Go OAuth 混用

### 9.1 Mastra 到底是什么

一句话：**TypeScript 里写 Agent / 工作流 / 记忆 / RAG 的应用框架**（类似「后端业务框架」），不是 Dify 那种「装完就有运营后台的平台」。

| 它自带（现成） | 通常仍要你们做 |
|----------------|----------------|
| Agent、Tool、Workflow | 产品 UI（建议 assistant-ui） |
| Memory（滑动窗口/工作记忆/语义回忆） | **业务账号、额度、审计、App 对接** |
| RAG 流水线 + 向量存储适配 | 复杂 PDF 深度解析（不够时再挂 RAGFlow） |
| Storage 适配器（libSQL / **PostgreSQL** 等） | 运营后台、品牌、计费展示 |
| 可挂 Next 或独立 Node 服务 | 不要用其 `ee/` 商业 SSO（自研或接你们 OAuth） |

License：核心 **Apache-2.0**；`ee/` 勿用。

### 9.2 你们已有 Go OAuth 注册中心 —— 怎么混、会不会更快

**可以混，而且推荐这样拆：**

```
使用方 App / H5
    → Go OAuth / 换票 / 额度 / 审计   （你们已有，继续用）
    → Mastra（TS）Agent + RAG + 对话流式
    →（可选）RAGFlow 只做难文档检索
    → 国内 LLM API
```

| 做法 | 评价 |
|------|------|
| **Go 管身份与额度，Mastra 管问答 Agent** | **推荐**：复用现成 OAuth，Phase 1 最快 |
| Mastra Next 全栈再重做一套登录 | 慢且重复，无必要 |
| Mastra 自带 Better Auth 等 | 可做 Demo；有 Go OAuth 时不必换 |

鉴权落地：Go 发 Session/JWT → H5 调 Mastra 路由时带 Token → Mastra 侧中间件验签（调 Go 的 JWKS/共享密钥，或只让 **Go BFF 反代** Mastra，对外只暴露 Go）。  
**更稳的混用：对外只暴露 Go；Go 校验通过后转发到内网 Mastra。** 这样 Mastra 不直接对公网，安全简单。

### 9.3 「Mastra + Next 全栈 + Go」会更快吗

| 组合 | 是否建议 | 说明 |
|------|----------|------|
| **Go（OAuth/额度）+ Mastra（Agent API）+ React/Vite H5（assistant-ui）** | **首选** | 职责清晰；不必强上 Next |
| Mastra + **Next 全栈**（页面+API 同仓）+ Go OAuth | 可以 | Next 适合要 SSR/同仓路由时；WebView H5 **不强制 Next**，Vite 往往更轻 |
| 只有 Next、不用 Go | 仅当放弃现有 OAuth | 你们已有 Go 中心，放弃反而慢 |

结论：**混用会更快**——快在「身份与额度不用重写」+「Agent/RAG 不用从零拼」。不是「Next 越多越快」。

### 9.4 数据存哪、是不是现成的

| 数据 | Mastra 是否现成 | 建议 |
|------|-----------------|------|
| 对话线程 / Agent 记忆 / Workflow 快照 | ✅ Storage 现成（开发 libSQL，生产 **PostgreSQL**） | 生产直接 PG |
| 向量 / RAG 块 | ✅ 有向量库适配；也可外置 | 简单语料用 Mastra；难文档外挂 RAGFlow |
| 用户、OAuth、会员、额度 | ❌ 不是 Mastra 职责 | **继续放 Go + 你们现有库** |
| 审计、业务订单 | ❌ | Go 侧 |

切换存储一般是换适配器配置；已有数据跨库需迁移，一期定 PG 即可。

### 9.5 后期怎么定制

| 扩展 | 方式 |
|------|------|
| 新能力（查库存、生海报） | 加 **Tool**，Agent 自动选用 |
| 多步流程 | **Workflow**（确定性步骤 + LLM 步骤） |
| 改提示词/模型 | Agent 配置，不必改前端 |
| 商品卡片 UI | assistant-ui 自定义消息；Tool 返回结构化 JSON |
| 换模型 | Model router / provider 配置 |

这些是框架主战场，比在纯 Go 里从零做 Agent 循环快。

### 9.6 为何本场景可优先 Mastra（相对 Python）

- 团队无 Python → **排除 LangGraph 作主栈**（与 04 文 N3 风险一致）  
- 有 Go OAuth → **不必**为鉴权再学一套平台  
- 要快交付 C 端助手 → Mastra + assistant-ui 同语言  

### 9.7 Python 里谁对标 Mastra（「可部署 Agent 应用服务 + 你们只做包装」）

| 对标维度 | **Mastra (TS)** | **Agno (原 Phidata)** | **LangGraph 开源库** | **LangGraph Agent Server 商业部署** | **Dify API** |
|----------|-----------------|------------------------|----------------------|-------------------------------------|--------------|
| 定位 | Agent 应用运行时 | **最接近的 Python 对标**：框架 + AgentOS 可当服务跑 | 编排库，要自己拼服务 | 官方可部署 Agent 服务 | 应用平台，API 包装 |
| License | Apache-2.0（勿用 ee/） | **Apache-2.0** | MIT | 库 MIT；**官方 Server 生产常要商业许可** | Apache+附加条款 |
| 「直接当服务部署」 | ✅ Node/Next | ✅ **AgentOS**（Docker/REST，偏开箱） | ❌ 需自挂 FastAPI | ✅ 但商用钥匙风险 | ✅ 但平台感强 |
| Agent/Tool/Memory/RAG | ✅ | ✅（含 Team、Knowledge） | ✅（偏工作流） | ✅ | ✅ |
| 只做 Go 包装 | ✅ | ✅ | 中（包装面要自己开 API） | ✅（若拿得到许可） | ✅ |
| 文档解析深度 | 一般 | 一般（Python 生态好接） | 自拼 | 自拼 | 中 |
| 与你们约束 | 主推 | **Python 想对标就选它**；但团队无人懂 Python → 仍不推荐主路径 | 案例最多，交付慢于 Agno/Mastra | 私有化商务重 | 藏 UI 才能报价 |

**结论：**  
- Python 里「形态最像 Mastra、可商用、可部署、适合包装」的是 **Agno（Apache-2.0 + AgentOS）**。  
- **LangGraph** 是能力最强的编排标准，但默认是**库**不是开箱应用服务；官方一键 Server 又容易碰到**商业许可**。  
- 你们已定「无 Python 人力」→ 对标了解即可，**落地仍优先 Mastra + Go 包装**，不要为对标切 Python。

---

## 8. 本文结论

允许非 Go 时，**更快且仍像自研交付**的成熟组合是：

1. **有 Go OAuth 时的更快组合：** Go（身份/额度）+ **Mastra**（Agent/RAG）+ assistant-ui（见 §9）  
2. **文档极难时：** 同上 + RAGFlow 黑盒检索  
3. **同等 RAGFlow 架构、BFF 换 TS：** N1  
4. **极限配置赶工：** N4（Dify 仅 API）——商务与协议先过会  
5. **团队无 Python：不选 N3 作主栈**  
6. **禁止：** N5（裸交开源平台）
