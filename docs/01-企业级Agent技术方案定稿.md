## 0. RAGFlow 是干什么的（先讲清楚）

**RAGFlow = 开源的「企业知识库检索增强引擎」**，不是聊天前端产品，也不是你们要卖给使用方的那个 App。

它专门解决知识库里最难、最耗工期的一段：

| 它做的事 | 通俗理解 |
|----------|----------|
| 文档解析 | Word/PDF/表格等拆成可用文本与结构 |
| 分块与索引 | 切成可检索片段，建向量/关键词索引 |
| 混合检索 + 精排 | 按问题找出最相关的几段 |
| 引用溯源 | 回答能指回原文位置 |
| （可选）对话/Agent | 自带能力，**本方案不把它的 UI 当交付物** |

你们卖的是：**带品牌的 H5 问答 + 运营后台 + 与使用方 App 的集成**。  
RAGFlow 若采用，应是机房里的**黑盒中间件**（只走 API），和用 PostgreSQL、用 Redis 一样——使用方买的是你们的产品与实施，不是「帮我装个开源站」。

## 1. 需求约束（决策依据）

| 约束 | 含义 |
|------|------|
| 快速交付 | Phase 1 ≈ 半个月，基础召回问答可上线 |
| 少自研风险 | 解析/分块/混合检索/引用等不从零写 |
| 企业级成熟 | 高星、活跃、可商用协议 |
| **可卖自研** | 对外可见面必须是自研产品；忌「部署 Dify/RAGFlow 控制台交差」——难谈价钱 |
| 团队语言 | **Go 优先**；若纯 Go 无法在工期内达到商业级稳定，允许其他体系作引擎/备选 |
| C 端形态 | 自有 H5 嵌 App；自有运营后台 |
| 后期扩展 | 商品卡、海报/视频（Phase 2+） |

**结论先讲：**  
- **不要**把 Dify / RAGFlow / FastGPT 的**自带平台 UI**当交付物（你的商业顾虑成立）。  
- **可以**把 RAGFlow（或同类）当**不可见引擎**，外面全是 Go BFF + 自研前后台——这才是「快 + 稳 + 好报价」的平衡点。  
- **纯 Go 从零拼商业级知识库**：半个月很难做到完整稳定可靠；适合作为长期内核自研路线，不适合 Phase 1 唯一路径。

## 2. 独立调研结论（不止你原先列的框架）

### 2.1 开箱企业 RAG / Agent 平台（高星，少自研）

| 项目 | 约 Star | License | 定位 | 对本项目 |
|------|---------|---------|------|----------|
| **RAGFlow** | ~8.5 万 | Apache-2.0 | 深度文档理解 + RAG **引擎** | **推荐作黑盒引擎**（禁用其 UI 交付） |
| **Dify** | ~7 万级 | Apache-2.0 | 带完整控制台的 LLM **应用平台** | **不推荐作交付面**；作引擎也偏「平台感」，商务风险高于 RAGFlow |
| **FastGPT** | ~2.5 万+ | 需核验商用条款 | 轻量知识库产品 | 同样不适合「装完平台就交」 |
| KnowFlow 等二开 | 视分支 | 常为 AGPL | 在 RAGFlow 上补 RBAC | **AGPL 传染风险，商用慎用** |

### 2.2 Go 语言 Agent / RAG 库（有，但「不够开箱」）

| 项目 | 约 Star | License | 实情 |
|------|---------|---------|------|
| **Eino**（CloudWeGo） | ~1.2 万 | Apache-2.0 | 字节生产验证；编排/ADK 强；**RAG 治理、权限、增量仍要自研** |
| **LangChainGo** | ~0.95 万 | MIT | 社区案例相对多；仍是「积木」，不是成品知识库 |
| go-openai 等 | 高 | MIT | 仅模型 SDK，不是 Agent/RAG 产品 |

**直接回答「Go 里还有没有更成熟的选？」**  
有可选框架（Eino / LangChainGo），**没有**能满足你「企业级成熟 + 尽量少自研」的知识库成品。Go 适合做**业务壳（BFF）**和**高并发接入**，不适合作为「少自研 RAG 内核」的唯一赌注。

### 2.3 Mastra（你点名问的）

| 项 | 说明 |
|----|------|
| 定位 | TypeScript 原生 Agent 框架（Agent / Workflow / Memory / RAG / 可观测） |
| Star | ~2.6 万，活跃，已 1.0 |
| **License** | **双许可**：核心 **Apache-2.0**（可商用、可改、可闭源交付）；`ee/` 目录（Studio 的 SSO/RBAC 等）为 **Mastra Enterprise License**，生产使用需商业授权 |
| 企业用法 | **只用 Apache-2.0 核心**即可建 Agent+RAG；登录/RBAC **自研**，不要依赖 `ee/` |
| 适合 | Agent 工具链、工作流、与 React/Next 一体；文档解析深度通常弱于 RAGFlow |
| 不适合当唯一内核的原因 | 复杂 PDF/扫描件/表格的「企业知识库」仍建议挂专业 RAG 引擎 |

**评价：** Mastra 作为**企业级 Agent 应用层**是成熟、友好协议（避开 EE）的好选择；作为**复杂文档知识库引擎**不如 RAGFlow。

### 2.4 模型网关：NewAPI 不是必须

| 方案 | 形态 | Phase 1 |
|------|------|---------|
| NewAPI / OneAPI | 独立进程 + **管理 UI** | **不采用**（你的顾虑成立：像中转站，不宜当交付物） |
| LiteLLM | Python SDK 或 Proxy（Proxy 也有 UI） | 非 Go 主栈时可用 SDK 模式；一期非必须 |
| **代码内路由** | `go-openai` / 官方兼容客户端 + 主备 BaseURL | **一期推荐** |
| 小型 Go 库 | 如 `go-llm-provider`、社区 gateway SDK | 可选增强，非必须 |

国内主流模型（豆包、通义、DeepSeek、智谱等）均提供 **OpenAI 兼容接口**。一期用库改 `BaseURL` + 简单 fallback 即可，**你的要求合理，不必上 NewAPI**。

### 2.5 C 端对话 UI：Vercel AI SDK ≠ UI 首选

| 层 | 选型 | 说明 |
|----|------|------|
| **生产级对话 UI** | **assistant-ui**（首选） | 线程/流式/重试/附件/自定义消息（商品卡）成熟；~1.1 万 Star，MIT |
| **流式协议 / hooks** | Vercel AI SDK（可选） | 是「传输与状态原语」，官方 UI 模板偏 Demo，**不是** C 端成品 UI |
| 组合 | assistant-ui ± AI SDK data stream | 业界常见；后端是 Go 时用 assistant-ui 自定义 Runtime / data-stream 适配 SSE 即可 |

**结论：C 端 UI 首选 assistant-ui，不是 Vercel AI SDK。** AI SDK 最多当协议层，可不用。

## 3. 三条路线权衡（结合「Go 优先 + 好谈价钱」）

| 路线 | 做法 | 交付可报价性 | 工期/稳定性 | Go 占比 | 建议 |
|------|------|--------------|-------------|--------|------|
| **A. 引擎黑盒 + 自研壳** | RAGFlow 仅 API；Go BFF + 自研 H5/后台 | **高**（使用方看到的是你们的产品） | **高**（难活外包给引擎） | 业务层全 Go | **主推荐** |
| **B. 开源平台直接交付** | 部署 Dify/RAGFlow/FastGPT，用自带后台 | **低**（像集成商装开源，难卖人天/产品价） | 最快出 Demo | 几乎无 | **否决作交付形态** |
| **C. 纯 Go 自研 RAG** | Eino/LangChainGo + pgvector 全自建 | **最高**（纯自研叙事） | Phase 1 **风险大**；解析/召回易不稳 | 100% Go | 仅当使用方强绑「无第三方引擎」或二期重写内核 |
| **D. TS 全栈自研感** | Mastra（Apache 核心）+ assistant-ui | 高（自研应用） | Agent 快；复杂文档仍弱 | 低 | 团队 Go 为主时作备选，非默认 |

**商务话术建议（路线 A）：**  
交付物是「企业知识助手（自有前后端）+ 私有化部署与集成」；底层使用开源引擎组件，与使用 Nginx/Postgres 同类，**不向使用方交付该引擎的运营控制台账号作为产品本身**。合同写清：可见系统为平台方定制系统。

**若走路线 C：** 把 Phase 1 验收降为「小语料、固定格式、有限题集」；复杂 PDF/表格单独立项——否则半个月很难承诺「商业级完整稳定可靠」。

### 3.1 定稿一句话（主路径 = 路线 A）

> **RAGFlow 只作内网知识引擎（API，不交其平台 UI）→ Go BFF 作可售卖的企业壳 → React + assistant-ui 作 C 端 → 模型代码级主备。**

### 3.3 组件职责

| 组件 | 职责 | 交付给使用方的可见面 |
|------|------|-------------------|
| RAGFlow | 文档解析、向量、混合检索、引用 | **不可见**（或仅运维内网） |
| Go BFF | 身份、额度、审计、SSE、业务 API | API |
| H5 + assistant-ui | C 端对话体验 | **主产品界面** |
| 自研运营后台 | 语料上下架、配额、审计查看（调 BFF/引擎 API） | **运营界面** |
| 模型路由 | 库内主备 | 无独立 UI |

### 3.4 为何不是「Go + Eino 自建 RAG」

| 维度 | Eino/LangChainGo 自建 | RAGFlow + Go BFF |
|------|----------------------|------------------|
| 文档解析/表格/复杂 PDF | 大量自研或拼库 | 引擎成熟能力 |
| 混合检索 + 引用 | 自研拼装 | 开箱 |
| 半个月风险 | 高 | 低（联调与壳为主） |
| Go 诉求 | 全栈 Go | **核心业务壳仍是 Go**；重活外置 |

若未来团队要加深 Agent 编排，可在 BFF 侧引入 Eino/Mastra **只做 Tool 调度**，检索仍走 RAGFlow——分层，不推倒重来。

### 3.5 备选路径（何时换）

| 条件 | 改用 |
|------|------|
| 文档极简、更看重可视化工作流/Agent 编排 | **Dify** 替 RAGFlow 作引擎（同样 API 化，自研壳） |
| 团队强 TS、Agent/工具链是一等公民、文档不复杂 | **Mastra（仅 Apache 核心）+ assistant-ui**；复杂文档仍建议旁路 RAGFlow |
| 强制全链路纯 Go、接受自研与延期 | Eino 或 LangChainGo（**不推荐**作为本需求默认） |

## 4. 关键设计定稿

### 4.1 登录：两套身份

| 域 | 方案 |
|----|------|
| C 端用户 | 使用方 App 体系；**一次性授权码换 Session**（主） |
| 运营后台 | 自研账号 + RBAC（admin/operator/viewer） |

### 4.2 一次性授权码是否合理？

**合理，且建议作为生产默认。**

本质是缩小版 OAuth「授权码」：短期、单次、不进 URL 长期凭证。

| 方式 | 适用 |
|------|------|
| **一次性 code → HttpOnly Cookie/Session** | App WebView 生产推荐；防链接转发盗用 |
| 短时 JWT 放 Header | 服务端联调或强控 WebView 可接受 |
| 长期 Token 拼 URL | **禁止** |

浏览器策略默认：**受限访问**（游客低额度或强制登录），内部敏感库可改为禁止浏览器。

### 4.3 一期不用 NewAPI

**定稿：Phase 1 不上 NewAPI / OneAPI。**

实现：

```text
BFF 配置：
  primary:  { baseURL, apiKey, model }
  fallback: { baseURL, apiKey, model }
调用：go-openai（或等价）→ 失败/超时切 fallback → 记审计与用量
```

何时再考虑独立网关：多租户卖 Token、几十个渠道运营、非研发人员改线路——那是 Phase 2+ 运维命题，且应选**可白标/可无 UI 嵌入**的方案，而不是把 NewAPI 当产品交付。

### 4.4 幻觉与质量（诚实基线）

Phase 1 依赖引擎能力 + BFF 约束，不宣称「七层治理」：

1. RAGFlow 检索 + 引用强制带回  
2. System Prompt：无依据则拒答  
3. BFF 校验引用 ID 属于本轮召回  

更深 Rerank/事实校验进 Phase 2。

### 4.5 记忆

Phase 1：会话落库 + 滑动窗口。  
摘要压缩、跨端复杂记忆：Phase 2。

## 7. 分期

### Phase 1（约 15 工作日，环境与 Key 就绪起算）

- RAGFlow 部署与模型/Embedding 配置  
- 语料导入与召回调参（共同题集 Top3 ≥80%）  
- Go BFF：code 换票、额度、SSE、审计、安全钩子  
- assistant-ui H5 + App WebView 联调  
- 自研运营后台最小集（文档触发同步、配额、日志）  

**不做：** NewAPI、生图/视频、复杂商品推荐、等保测评、把 RAGFlow/Dify UI 当 C 端产品。

### Phase 2+

见 `03-Phase2高阶能力方案先行.md`（商品卡、模板海报、视频任务、Mastra/Eino 工具层可选）。

## 9. 对甲一页纸

1. 知识能力用 **RAGFlow**（成熟引擎），不是从零写 RAG。  
2. 产品形态是 **你们的 H5 + 运营后台**；引擎藏在内网。  
3. 接入层用 **Go BFF**（鉴权、额度、审计）。  
4. 对话 UI 用 **assistant-ui**。  
5. 模型 **代码级主备**，一期 **无 NewAPI**。  
6. Phase 1 只验收 **基础知识库问答**；多媒体与导购后期另签。
